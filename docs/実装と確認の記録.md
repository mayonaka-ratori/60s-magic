ローカル音声認識はKotoba-Whisper v2.0、faster-whisper 1.2.1、CTranslate2 4.8.2を使用しています。認識用ファイルは版 `f44edd35eaeb2274e85ac7b31fb2c6f59ff1c4bc` に固定しました。RTX 4070 SUPER 12GBで、読み込み後の合成音声一回分の認識は約110〜125msでした。これは話してから表示されるまでの時間ではありません。

合成音声では「分かれろ」が「ふんかれろ」、「氷よ」が「氷を」になる例があり、文字の完全一致ではありません。雷・七つ・氷・壁・攻撃しない指示が魔法に反映されることを確認しています。実際の人の声で同じ精度になることは未確認です。結果は `.local-speech/test-report.json` と `.local-speech/browser-test-report.json` に置き、Gitには含めません。

ブラウザーはChrome for Testing、描画はこのPCのDirect3D 11で確認しました。最初の自動確認で使ったソフトウェア描画では操作の送信が遅かったため、実機の画像処理を使う設定へ変更しています。実機の手の追跡が目標性能を満たしたという意味ではありません。

新しい術式の描画を本編へ接続した後、ローカル音声認識とマウスを使った24秒を再確認しました。一回の測定は平均59.75fps、フレーム間隔の99パーセンタイル16.9ms、発動17.009秒、最後の認識処理116.8msでした。合成音声を使用し、カメラは同時使用していません。人の手と声での精度・遅れの確認は別に残します。

その後、画像で動かす騎士と効果音を追加した回は平均56.63fps、フレーム間隔の99パーセンタイル18.5ms、発動17.010秒でした。こちらも合成音声とマウスです。[騎士と音の詳しい確認](騎士の動きと効果音.md)。

騎士を立体のモデルへ置き換えた回は、GPUのない開発用の環境で作業したため、速度を測り直していません。この環境はソフトウェア描画で、画像の騎士が毎秒1.7画面、立体の騎士が毎秒1.35画面でした。部品が40ほどと、にじむ光の処理が増えた分です。GPUのある実機ではどちらも軽い処理ですが、実機の数値ではありません。画面が遅いと0.62秒しかないひるみの姿勢を飛ばすため、`npm run test:browser` の被弾の確認もGPUのあるPCで行う必要があります。24秒を通して遊ぶブラウザーの確認も、この環境では操作が間に合わず終わってしまいます。置き換える前のコードでも同じところで止まったため、今回の変更による違いではありません。確認画面の3姿勢は時刻を止めて見るため、この環境でも通りました。

## Macで2回試したときの記録（2026年9月20日）

MacのCPUで `whisper-small` を使って2回続けて試したところ、どちらも最後の認識結果が間に合わず、途中結果で魔法を決めていました。サーバーの記録では、全部の声を含む最後の1回が2回とも `outcome: "closed"`、`finalDelivered` は `false` です。

- 1回目は11.6秒までの文字で確定し、13.2秒までの文字（「抜け、バービュード、アークライド」まで入っていた）を捨てていました。
- 2回目は13.0秒までの文字で確定し、14.0秒までの文字を捨てていました。
- 認識にかかる時間は声が伸びるほど長くなります。0.4秒の声で1.07秒、11.6秒で1.56秒、13.2秒で1.70秒でした。
- 2回目は出だしの2回が4.5秒と4.3秒かかり、最初の文字が画面に出たのは10.1秒でした。前のプレイの演出やカメラの処理とCPUを取り合ったと見ています。
- 1回目は14.0秒に音声認識との接続が `1008` で切れ、「音声認識との接続が切れました。描いた線で続けます。」が画面に出ていました。実際には途中結果を使えていたので、表示と中身が食い違っていました。

これを受けて次のように直しました。

- 最後の文字を待てる時間を650msから1100msへ広げました。声の最後の結果が届いたらその場で次へ進み、届かないときだけ15.1秒で切り上げます。
- Jevへ送る時刻を14.7秒固定から「文字が届き次第、遅くとも15.1秒」へ変えました。打ち切りは15.9秒です。16秒の確定と17秒の発動は変えていません。
- 締め切りに間に合わない認識を始めないようにしました。直前の処理時間から見込み、間に合わないときは認識を始めずに終わりの合図を返します。結果を捨てるだけの処理でCPUを使わなくなります。
- 順番が前後した音、受付が終わった後に届いた音、14秒を超えた音で接続を切るのをやめ、その分だけ捨てて続けるようにしました。形が壊れた音と、外れた音が200回を超えた場合だけ接続を切ります。
- 確認用の記録に、捨てた音の数（`droppedChunks`）と、その回に待てる時間（`waitMs`）を足しました。

通ったのは単体の試験69件と、型の確認とビルドです。この作業用のLinux環境ではブラウザーの描画が遅く、24秒を通しで遊ぶ試験は時間切れになります。Jevの期限に関わる2件は通りました。実際のMacで最後の文字が入るようになったかは未確認です。次に試すときは、確認用の記録で `finalDelivered` が `true` になるか、`outcome` が `closed` の回が減るかを見てください。

## MacのGPUで音声認識を動かせるようにした（2026年9月20日）

CPUだけでは日本語に強いモデルが間に合わないので、Apple SiliconのMacではMacのGPUを使う道を用意しました。使っているPCの値は [確認に使うPC](確認に使うPC.md) にまとめています。

- `speech/engines.py` を足して、動かし方を二つにしました。`faster`（faster-whisper。NVIDIAのGPUとCPU）と `mlx`（mlx-whisper。MacのGPU）です。呼ぶ側はどちらも同じ形で使います。
- 置いてある認識ファイルの形（`model.bin` か `weights.npz`）で動かし方が決まります。合わないときは、何をどう直すかを書いたメッセージで止まります。
- モデルの選択肢を増やしました。末尾が `-mlx` のものがMacのGPU用です。Apple SiliconのMacの初期値は `kotoba-v2.0-mlx`、WindowsとNVIDIAのGPUは今までどおり `kotoba-v2.0`、それ以外は `small` です。
- `npm run benchmark:speech` で、準備できているモデルの速さを同じ音声で比べられます。3秒、7秒、11秒、14秒の長さで測り、14秒ぶんが1.1秒以内なら最後の言葉が間に合う、という判定を出します。
- `npm run make:speech-fixtures` がMacでも動くようになりました。Macの読み上げ機能で16kHzの音声を作ります。日本語の声が入っていなければ、追加する場所を案内して止まります。
- `mlx-whisper` は Apple Silicon の Mac だけに入ります。Windows と Linux の準備内容は変わりません。

通ったのは単体の試験70件と、型の確認とビルドです。**実際のMacでは何も動かしていません。**mlxが読み込めるか、`kotoba-v2.0-mlx` が14秒の詠唱に間に合うか、聞き取りがどれだけ良くなるかは、次にMacで試すときに確かめてください。初回の準備でモデルを取り直すので、1.5GBほどの通信がかかります。

Macで確かめる順番は、`npm run setup:speech` → `npm run make:speech-fixtures` → `npm run benchmark:speech` です。最後のコマンドが各モデルの時間と「間に合うか」を出します。間に合わないモデルしかなければ、確定の時刻を後ろへ動かす判断になります。

## 聞き取りの揺れを辞書へ寄せるようにした（2026年9月20日）

モデルを変えなくても直せる間違いがあるので、辞書側でも拾えるようにしました。今までは完全に同じ文字でなければ読み替えない作りでした。

寄せるのは書き方の揺れだけです。伸ばす音（「らいてー」と「らいてい」）と濁点の抜け（「くれん」と「ぐれん」）を同じ音として扱います。ただし、元がかなで書かれていること、文字数が変わらないこと、四文字までは揺れだけ（五文字以上は一文字の違いまで）という三つを満たすときに限ります。

この条件にしたのは、漢字で書かれた普通の言葉を動かさないためです。「効果」と「業火」は濁点を外すと同じ音になりますが、漢字で書かれていれば寄せません。「ならくじ」を「奈落」に、「ふんかれろ」を「分かれろ」にすることもありません。前後の文字を見る今までの決まりもそのまま通します。

どこを寄せたかは確認用の記録の `corrections` に残ります。元の聞き取りは今までどおり `rawTranscript` です。

聞き違いが決まった形で繰り返される場合は、辞書の `spellings` にその表記を足せば完全一致で拾えます。実際のプレイで何と言って何と聞き取られたかが分かってから足す方針です。

単体の試験75件が通りました。合成音声や人の声での効果は、次にMacで試すときに `corrections` を見て確かめてください。
