# 保留時のまとめと再開の手順

2026年9月23日に、ハッカソンでの紹介を終えて開発を保留にしました。この文書は、再開するときに最初に読むものです。どこまでできたか、作りながら分かったこと、再開したら何から手を付けるかをまとめています。細かい確認の状態は[実装と確認の記録](実装と確認の記録.md)にあります。

## 1. 保留にした時点の状態

- 90秒の流れ（一回目の魔法、防御の回、とどめの回）と、結果画面（魔導書）まで作ってあります。
- 遊び方は二つです。標準の「順番に」（一回目は声だけ、防御は手だけ、とどめは手のあと声）と、選べる「同時に」（三回とも描きながら唱える）です。
- 2026年9月20日から23日の4日間で、234件のコミットを積みました。
- ハッカソンで紹介できました。
- 最後に試験を走らせた結果は次のとおりです。
  - 単体の試験831件（2件は飛ばす）と配布用の生成は、9月23日にこの作業環境とWindowsで通りました。
  - ブラウザーの試験は、今の版ではWindowsで15件が通っただけです。Macでは、その前の版で28件が全部通っています。
- 人が今の90秒版を遊んで、目と耳で確かめる確認はまだです。人がMacで遊んで確かめたのは、24秒と60秒だったころまでです。
- QRの先の公開ページ、曲と効果音の素材、会場での長時間の運転の確認は手付かずです。

GitHubの状態は次のとおりです。

- メインにすべて取り込み済みです。
- メインに入っていない枝が一つあります。`claude/mobile-game-guide-page-uka281` で、QRで開くスマホ向けの遊び方の案内ページです。再開したときに取り込むかを決めます。

## 2. 作りながら分かったこと

### 時刻の決め方

- 秒数をあちこちに書くと、必ずずれます。実際に、マイクが一回目の途中（14秒）で止まる、Googleの聞き取りが20秒で切れる、Python側だけ14秒分しか音を受け付けない、といった不具合がすべて「古い秒数が一か所に残っていた」ことから起きました。
- 時刻を `src/game/rounds.ts` の表一つから作る形にしてからは、90秒への作り直しや「順番に」の追加でも、ずれがほぼ出なくなりました。再開後もこの決まりは守ります。
- 試験も、秒数を書き並べるのではなく表から作ります。そうしないと、時間を変えたとたんに試験が全部落ちます。

### 遊び方

- 描きながら唱えるのは、初めての人には難しいと分かりました。そこで、回ごとに手と声を分ける「順番に」を作って標準にしました。「同時に」は慣れた人向けに残しています。
- 回の始まりや、とどめで「描く」から「唱える」へ変わるところでは、大きな文で今やることを伝える必要がありました。
- 防御の盾は、言葉よりも「自分がこう描いたからこうなった」と分かることを優先しました。囲う、線を掛ける、離して描く、で止め方が変わります。ただ、この割り当てで伝わるかは、人に試してもらわないと分かりません。

### 音声認識

- 声はこのPCの中で聞き取ります（MacはGPUで `kotoba-v2.0-mlx`、Windowsは `kotoba-v2.0`）。
- 認識の手掛かりとして語を渡すと、かえって悪くなることがありました。Macでは渡さない設定にしています。41語渡すと短い声が空欄になりました。
- 雷霆、氷晶、霹靂、紅蓮などの難しい言葉は、今のモデルでは聞き取れません。モデルを直すのではなく、聞き違い（例：かみなり→カメナリ、亀なり）を辞書で受け止める方法で対応しました。
- 難しい言葉を使う遊び方にするなら、言葉の選び方か、聞き取りの方法そのものを見直す必要があります。

### 手の認識

- 手が画面の端に出ると見失います。取れる点が極端に少ない回がありました。しきい値を下げ、350ミリ秒までの途切れは同じ線として続けるようにしましたが、直した後の追従はまだ人の手で確かめていません。

### 演出

- 防御の回に一回目の詠唱の量まで足していたせいで、何をしても同じ派手さになる不具合がありました。「入力によって見た目が変わるか」は、数字で確かめないと気付けません。
- 大型タイトルの演出を調べて入れたこと（画面全体を使う、敵の足踏みや溜めで圧を出す、止めて見せる間を作る）は、画面写真で見る限りは効いています。人が見てどう感じるかはまだです。
- 外部の返事（Jev）が遅れても演出を延ばさない、再試行しない、という決まりのおかげで、90秒の流れが崩れません。

### 試験と確認のしかた

- 「試験が通った」と「人が遊んで確かめた」は別物です。記録では必ず分けて書きました。再開後もこの分け方を続けます。
- Mac用とWindows用で描画の設定が違い、Macでブラウザーの試験が全部落ちたことがありました。本番のPC（Mac）で走らせないと分からない不具合があります。
- 実装と同じ式を書いた試験は、実装が壊れても通ってしまいます。固定の値で確かめ、わざと実装を壊して落ちるかを見ると、役に立つ試験かどうか分かります。
- 試験は増やしすぎると走らせにくくなります。9月22日に単体の試験を621件から486件、ブラウザーの試験を26件から17件に減らしました。
- 複数の人（Claudeを含む）にコードを読んでもらうと、自分では気付かない不具合が毎回見つかりました。
- Claudeの作業環境では画面が1秒に1コマほどしか進みません。仮の時計で進めて画面写真を撮る道具を作り、流れを見ました。

### 記録の大きさ

- 一回遊んだ記録は、いちばん重い場合で片手約143KBです。設計仕様の目安（圧縮後100KB程度）を超えています。公開ページへ送る前に、間引くか圧縮するかを決めます。

## 3. 再開したら最初にすること

1. メインを最新にして、`npm install` のあと `npm test` と `npm run build` が通るかを見ます。
2. MacでREADMEの手順どおり、音声認識の準備（`npm run setup:speech`）をします。
3. Macで、`npm run test:speech`、`node scripts/prepare-browser-audio.mjs`、`npm run test:browser` の順に走らせます。今の版はMacでまだ走らせていないので、ここで落ちる所があれば先に直します。
4. `npm run dev` で起動し、`http://localhost:5173/` をヘッドセットで一度通して遊びます。見る所は[実装と確認の記録](実装と確認の記録.md)の「Macで次に確かめる手順」にあります。
5. 下の「今後の進め方」から次にやることを選びます。

## 4. 今後の進め方

上から順に進めるのがおすすめです。

### 第1歩：今の版を人で確かめる

- 自分で「順番に」と「同時に」を通して遊び、声が拾えるか、手で描けるか、合図が伝わるかを見ます。
- 初見の人に5人ほど遊んでもらいます。手順は[人に試してもらう手順](人に試してもらう手順.md)にあります。
- 決まっていないことをここで決めます（[順番に入力する遊び方](順番に入力する遊び方_設計.md)の「まだ決めていないこと」）。
  - 「順番に」の一回目で声を受け付ける時間の長さ。声だけだと長すぎるかもしれません。
  - 防御の止め方の割り当て（囲う、線を掛ける、離して描く）で良いか。
- ハッカソンでもらった感想があれば、ここで一緒に見直します。

### 第2歩：持ち帰りを作る

- QRの先の公開ページを作ります。ゲーム側でやることは[公開ページへ送る：ゲーム側の作業手順](公開ページへ送る_ゲーム側の作業手順.md)にまとめてあります。
- 送る前に、記録の大きさ（約143KB）をどうするか決めます。
- スマホ向けの遊び方の案内ページ（メインに入っていない枝）を取り込むかを決めます。

### 第3歩：見た目と音を仕上げる

- 曲と効果音の素材を置きます（[音素材の入れ方](音素材の入れ方.md)）。
- 着弾のコマ絵や騎士の部位分けなど、作る予定の素材を入れます（`docs/references/` の指示文）。
- Jevへの質問を12問から24問へ広げます（設計仕様の第四段階）。

### 第4歩：会場で動かす準備

- 会場のMacで、長時間（4時間）動かし続けても止まらないか、熱くならないかを見ます。
- カメラやマイクが外れたときなど、会場の機器トラブルへの対応を決めます。
- Jevとの実通信を何度も試し、返事が安定して間に合うかを見ます。
