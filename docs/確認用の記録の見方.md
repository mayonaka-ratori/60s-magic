# 確認用の記録（JSON）の見方

`?dev=1` を付けて開いたときの「記録を保存する」で落ちるJSONファイルの、見るべき場所をまとめます。声がうまく拾えない、線の反応が遅い、といったときに、どこで時間がかかっているかをこのファイルで確かめます。中身は `src/main.ts` の `report()`、`src/game/battle.ts` と `src/game/session.ts` の `report()`、`src/game/diagnostics.ts` で作っています。

## 保存の仕方

- `localhost:5173/?dev=1` で開き、結果の画面で「記録を保存する」を押す。ブラウザーのダウンロード先に `魔法の記録_〜.json` ができる。「確認用の記録を見る」なら画面の中で読める。
- 途中で「中止する」を押した回も、開始画面の「前回の記録を保存する」で保存できる。
- 保存されるのは時刻と文字と点列だけで、音声や映像は入らない。詠唱した言葉の文字は入るので、人に試してもらったときは本人に伝える。

## どちらの遊び方の記録か：`flow`

`flow` が `sequential` なら「順番に」、`together` なら「同時に」です。回の秒数は遊び方で違います（[動きの詳細](動きの詳細.md)の「回ごとの時刻」）。回ごとの受付の時刻は、各回の `state.inputWindow` にも入っています。`drawEndSessionMs` が描く締め切り（`null` なら描かない回）、`voiceStartSessionMs` が声の受付開始（`null` なら声を使わない回）、`motionAndSpeechConcurrent` は「同時に」なら `true` です。

## 時刻の読み方

- 出来事の時刻（`diagnostics.events` の `atMs`、`arrivals` と `lastResult` の `arrivedMs`、`rounds[i].events` の `atMs`）は、90秒が始まった瞬間を0としたミリ秒です。準備の合図の間の出来事は負の値になります。
- 声の時刻は、その回の始まりを0として数えます。`rounds[i].speechEntries` の `startMs` と `endMs`、`diagnostics.voice` の `firstAudioMs` と `lastAudioMs`、`arrivals` の `startMs` と `endMs`、`lastResult.coversUntilMs` がそうです。通しの時刻に直すには、その回の始まり（`state.inputWindow.startSessionMs`）を足します。「順番に」のとどめは50000、「同時に」の防御は30000、とどめは56000です。
- 「順番に」のとどめは描く時間のあとに声を受け付けるので、声の時刻は12000ほどから始まります。

## まず見る場所

### 声が遅れていないか：`diagnostics.voice`

声を受け付けた回（「順番に」は一回目ととどめ、「同時に」は三回とも）の分がまとめて入ります。

| 項目 | 意味 |
| --- | --- |
| `audioChunksSent` / `audioBytesSent` | マイクの音をサーバーへ送った回数と量。0なら声が拾えていない（マイクの許可を疑う） |
| `firstAudioMs` / `lastAudioMs` | 最初と最後に送った音の時刻（回ごとの時刻） |
| `resultsReceived` | 文字になった結果が何回届いたか。0なら認識が一度も終わっていない |
| `finalReceived` | どこかの回で、締め切りまでの音を含む最後の結果が届いたか。回ごとに見るときは、サーバー側の `speechSessions` の `finalDelivered` を見る |
| `lastResult` | 最後に届いた結果。`delayMs` は `arrivedMs` から `coversUntilMs` を引いた値。一回目の結果ならそのまま音の最後から文字が届くまでの遅れだが、二回目からの結果はその回の始まりの分だけ大きく出るので、それを引いて読む |
| `processingMs` | 認識そのものにかかった時間の平均と最大。NVIDIAのGPUなら0.1秒ほど、MacのGPUなら約1秒、CPUなら数秒になることがある |
| `arrivals` | 届いた結果の一覧。`endMs`（どこまでの音か、回ごとの時刻）と `arrivedMs`（いつ届いたか、通しの時刻）を見比べる。二回目からは上と同じく回の始まりを足してから比べる |

`speechFallback` が `true` のときは、どこかの回で確定が間に合わず、最後の途中結果を魔法に使っています。どの回かは `rounds[i].usedFallback` で分かります。

### 手の認識が重くないか：`diagnostics.camera`

`delegate` が `GPU` なら、手を探す処理をMacやPCのGPUで動かせています。`CPU` になっていたら、GPUを使えずCPUへ戻った回です。`detectMs` が手を探す処理そのものの時間、`latencyMs` は画面へ返ってくるまでの時間です。

```json
"camera": { "delegate": "GPU", "frames": 700,
  "detectMs": { "average": 4.2, "p99": 9.1, "max": 22 },
  "latencyMs": { "average": 7.8, "p99": 14, "max": 31 } }
```

`detectMs` の平均が10ミリ秒を超えていたら、手の認識がCPUを食っています。`diagnostics.events` の「手の認識の準備ができた」にある `warmupMs` が準備にかかった時間です。90秒が始まる前に済ませているので、この値が大きくてもプレイ中には影響しません。

### 線の反応が遅くないか：`diagnostics.drawing` と `measurement`

| 項目 | 意味 |
| --- | --- |
| `drawing.pointerToFrameMs` | マウスや手の入力が来てから、次に画面を描くまでの時間。`p99` が50を超えると引っかかりを感じやすい |
| `drawing.frameMs.p99` | 画面の描き替えの間隔。16.7が理想で、33を超えるとカクつく |
| `drawing.framesOver50Ms` | 50ミリ秒以上止まった回数 |
| `drawing.averageFps` | 1秒あたりの描き替え回数。60に近いほどよい |
| `measurement.inputToDrawMs` | 入力を受け取ってから、その入力を含む描画を終えるまで。`median` と `p95`。0.1秒以内が目安 |

CPUで音声認識を動かしていると、認識の最中に描画が遅くなることがあります。音声を切って同じ操作をしたときの値と見比べてください。

### 何がいつ起きたか：`diagnostics.events`

準備の開始、準備の合図、90秒の開始、確認番号の用意、音声認識への接続、録音の開始と停止の指示、声の受付（二回目からのつなぎ直し）、入力の受付の終了、入力の確定、Jevの返事、魔法の確定、結果の表示が時刻つきで並びます。回ごとの出来事には `round` が付きます。「Jevの返事なし」「声を受付できず」「声の接続が切れた」があれば、その理由も入っています。「入力を確定」には、そのときの聞き取りの文字、辞書へ寄せた記録、盾の決め方も入ります。

## サーバー側の記録：`server`

| 項目 | 意味 |
| --- | --- |
| `machine` | OS、CPUの数、Node.jsの版 |
| `localSpeech.status` | 認識の状態。`device`（cpu/cuda/gpu）、`threads`（使うCPUの数）、`loadMs`（読み込みにかかった時間） |
| `localSpeech.recentJobs` | 直近の認識一回ごとの、音の長さ・待ち時間・処理時間 |
| `localSpeech.rejectedBusy` | 処理が追いつかず断った回数。多ければCPUが足りていない |
| `speechSessions` | 直近5回の受付ごとの要求と結果（一回遊ぶと、「順番に」なら2つ、「同時に」なら3つ）。`outcome` が `deadline` や `closed` の要求は、間に合わず捨てた結果。`waitMs` はその回に最後の声を待てた時間、`droppedChunks` は捨てた音の数、`finalDelivered` は最後の声を含む結果を届けられたか。聞き取った言葉は入らず、文字数だけが入る |

## 回ごとの記録：`rounds`

一回分の記録が配列に並びます。`rounds[0]` が一回目、`rounds[1]` が防御、`rounds[2]` がとどめです。三つとも同じ形です。

| 項目 | 意味 |
| --- | --- |
| `round` / `castId` | `first`、`defend`、`finish` のどれか。Jevへ送るときの区別に使う番号（`cast-01` など）も入る |
| `state` | Jevへ送った内容そのもの。`speech.rawTranscript` が聞き取った文字、`speech.normalizedTranscript` が辞書へ寄せた後の文字、`inputWindow` がその回の受付の時刻、`previous` が前の回の魔法 |
| `recipe` | 決まった魔法。`source` が `jev` ならJevの返事、`local` ならPC内の規則、`mixed` なら両方を合わせて決まっている |
| `jev` | Jevの返事そのもの。届かなければ `null` |
| `guard` | 防御の回だけ入る。ほかの回は `null`。下の表を見る |
| `speechEntries` / `usedFallback` | 採用した聞き取りと、確定が間に合わず途中の結果を使ったか |
| `corrections` | 聞き取りの書き方を辞書へ寄せた記録。下を見る |
| `events` | その回の場面の切り替わりと確定の時刻。「順番に」のとどめでは、描く締め切りの `drawing-ended` も入る |
| `voiceLayers` | 声で積んだ言葉の部品。`kind` は種類、`active` が `false` なら言い直しで薄くなった部品。締め切り後は増えない。「順番に」の一回目ととどめだけに入り、ほかは空 |
| `rawPoints` / `displayPoints` | 本人が描いた点列と、表示用に間引いた点列 |

### 防御の回：`rounds[1].guard`

| 項目 | 意味 |
| --- | --- |
| `enclosed` | 狙いの印を囲めたか。囲めなくても防げるので、失敗の印ではない |
| `rings` | 何重に囲んだか |
| `moved` | 囲めず、印の範囲にも線が無く、一番近い線を印の前へ運んだか |
| `kind` | 盾の形。`ring`（輪）、`wall`（横長）、`pillar`（縦長）、`orb`（小さい動きか、線が無いとき） |
| `layers` | 重なった層の数。1〜5 |
| `style` | 止め方。`block`（受け止める）、`reflect`（弾き返す）、`erase`（かき消す）。「順番に」では描いた形で、「同時に」では言葉で決まる |

`enclosed` と `moved` がどちらも `false` なのに `kind` が `orb` 以外なら、囲えなかったが印の範囲に掛かった線をそのまま盾にした回です（その線が小さいと `orb` になることもあります）。人に試してもらったとき、`enclosed` が `false` ばかりなら、印の大きさか位置を見直す材料になります。

### 辞書へ寄せた言葉：`rounds[i].corrections`

書き方の揺れを辞書の言葉へ直したときに、一件ずつ入ります。`from` が聞き取れた文字、`to` が寄せた先、`reading` が辞書の読みです。

```json
"corrections": [{ "from": "らいてー", "to": "雷霆", "reading": "らいてい" }]
```

空の配列なら、寄せずに済んだということです。元の聞き取りは同じ回の `state.speech.rawTranscript` に残っているので、寄せ方が合っているかを見比べられます。

## 戦い全体の項目

次の項目は戦い全体で一つです。

| 項目 | 意味 |
| --- | --- |
| `sessionId` / `flow` / `scope` / `cancelled` | 遊びの番号、遊び方、記録の範囲（`full-90-seconds`）、中止したか |
| `inheritedNodes` | 前の回から引き継いだ光点の数 |
| `mode` / `feedback` / `calmMode` | 入力の方法（`pointer`、`camera`、見本なら `demo`）、感想の回答、控えめモードだったか |
| `confirmCode` | 6桁の確認番号 |
| `storedLocally` / `storeAvailable` / `saveState` / `saveFailure` | このPCのブラウザーの中へ保存できたか、保存先が使えたか、保存の状態、失敗の理由 |
| `speechFallback` | どこかの回で途中の聞き取りを使ったか（上を見る） |
| `audio` | 効果音の状態。`microphone` はマイクを使ったか、`ducked` は記録を作った瞬間に曲と効果音を下げていたか、`events` は鳴らした音の一覧、`samples` は素材の読み込み。`recordingQuiet` は今は常に `false`（録音中も効果音を鳴らす） |
| `composite` | 合成の後処理を使ったか、途中で諦めたか、その間の速さ |
| `measurement` | 平均fps、描き替え間隔の99パーセンタイル、カメラの処理時間、上の `inputToDrawMs` |
| `recordedAt` / `userAgent` / `screen` | 記録を作った時刻、ブラウザー、画面の大きさ |

`audio.events` では、騎士の足踏み（`step`）と盾打ち（`clang`）が声の受付中にも鳴っていること、印を囲えたときの `ring` を確かめられます。結果の画面を出すときに音を止めるので、そのあとに作った記録の `ducked` は `false` です。

## このPCのブラウザーに残る遊んだ記録

確認用のJSONとは別に、遊んだ記録（確認番号、三つの魔法、描いた線、詠唱の文字）がブラウザーの中に残ります。中身は `src/game/record.ts` の `StoredPlay` です。ここにも `flow` が入ります。`flow` が無い古い記録は、一回目に声の円の色（`rounds[0].voiceColors`、空の配列も含む）があれば「順番に」、なければ「同時に」として読みます。引き継いだ光点の色は `inherited[].element` に残ります。
