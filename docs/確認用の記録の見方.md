# 確認用の記録（JSON）の見方

`?dev=1` を付けて開いたときの「記録を保存する」で落ちるJSONファイルの、見るべき場所をまとめます。声がうまく拾えない、線の反応が遅い、といったときに、どこで時間がかかっているかをこのファイルで確かめます。

## 保存の仕方

- `localhost:5173/?dev=1` で開き、結果の画面で「記録を保存する」を押す。ブラウザーのダウンロード先に `魔法の記録_〜.json` ができる。「確認用の記録を見る」なら画面の中で読める。
- 途中で「中止する」を押した回も、開始画面の「前回の記録を保存する」で保存できる。
- 保存されるのは時刻と文字だけで、音声や映像は入らない。詠唱した言葉の文字は入るので、人に試してもらったときは本人に伝える。

時刻はすべて、90秒が始まった瞬間を0としたミリ秒です。防御の回の出来事も、30秒からの通しの時刻で入ります。声の時刻だけは回ごとに0から数え直すので、`rounds[1].speechEntries` の時刻には24000を、`rounds[2].speechEntries` の時刻には40000を足して読みます。

## まず見る場所

### 声が遅れていないか：`diagnostics.voice`

| 項目 | 意味 |
| --- | --- |
| `audioChunksSent` | マイクの音を何回サーバーへ送ったか。0なら声が拾えていない（マイクの許可や無音の判定を疑う） |
| `firstAudioMs` / `lastAudioMs` | 最初と最後に音を送った時刻 |
| `resultsReceived` | 文字になった結果が何回届いたか。0なら認識が一度も終わっていない |
| `finalReceived` | 14秒の終わりの確定結果が届いたか。`false` なら途中結果しか使えていない。サーバー側の `finalDelivered` も同じ意味 |
| `lastResult.delayMs` | 最後の結果について、音の最後の時刻から文字が届くまでの遅れ。CPUで動かすと大きくなる |
| `processingMs` | 認識そのものにかかった時間。NVIDIAのGPUなら0.1秒ほど、MacのGPUなら約1秒、CPUなら数秒になることがある |
| `arrivals` | 届いた結果の一覧。`endMs`（どこまでの音か）と `arrivedMs`（いつ届いたか）を見比べる |

`speechFallback` が `true` のときは、確定が間に合わず、最後の途中結果を魔法に使っています。

### 手の認識が重くないか：`diagnostics.camera`

`delegate` が `GPU` なら、手を探す処理をMacやPCのGPUで動かせています。`CPU` になっていたら、GPUを使えずCPUへ戻った回です。`detectMs` が手を探す処理そのものの時間、`latencyMs` は画面へ返ってくるまでの時間です。

```json
"camera": { "delegate": "GPU", "frames": 700,
  "detectMs": { "average": 4.2, "p99": 9.1, "max": 22 },
  "latencyMs": { "average": 7.8, "p99": 14, "max": 31 } }
```

`detectMs` の平均が10ミリ秒を超えていたら、手の認識がCPUを食っています。`diagnostics.events` に「手の認識の準備ができた」があり、そこの `warmupMs` が準備にかかった時間です。24秒が始まる前に済ませているので、この値が大きくてもプレイ中には影響しません。

### 線の反応が遅くないか：`diagnostics.drawing`

| 項目 | 意味 |
| --- | --- |
| `pointerToFrameMs` | マウスや手の入力が来てから、次に画面を描くまでの時間。`p99` が50を超えると引っかかりを感じやすい |
| `frameMs.p99` | 画面の描き替えの間隔。16.7が理想で、33を超えるとカクつく |
| `framesOver50Ms` | 50ミリ秒以上止まった回数 |
| `averageFps` | 1秒あたりの描き替え回数。60に近いほどよい |

CPUで音声認識を動かしていると、認識の最中に描画が遅くなることがあります。音声を切って同じ操作をしたときの値と見比べてください。

### 何がいつ起きたか：`diagnostics.events`

準備の開始、90秒の開始、録音の開始と停止、防御の回の声の受付、入力の確定、Jevの返事、魔法の確定、結果の表示が時刻つきで並びます。回ごとの出来事には `round` が付きます。「Jevの返事なし」があれば、その理由も入っています。

## サーバー側の記録：`server`

| 項目 | 意味 |
| --- | --- |
| `machine` | OS、CPUの数、Node.jsの版 |
| `localSpeech.status` | 認識の状態。`device`（cpu/cuda/gpu）、`threads`（使うCPUの数）、`loadMs`（読み込みにかかった時間） |
| `localSpeech.recentJobs` | 直近の認識一回ごとの、音の長さ・待ち時間・処理時間 |
| `localSpeech.rejectedBusy` | 処理が追いつかず断った回数。多ければCPUが足りていない |
| `speechSessions` | 受付ごとの要求と結果。`outcome` が `deadline` や `closed` の要求は、間に合わず捨てた結果。`waitMs` はその回に最後の声を待てた時間、`droppedChunks` は捨てた音の数、`finalDelivered` は最後の声を含む結果を届けられたか |

### 辞書へ寄せた言葉：`corrections`

書き方の揺れを辞書の言葉へ直したときに、一件ずつ入ります。`from` が聞き取れた文字、`to` が寄せた先、`reading` が辞書の読みです。

```json
"corrections": [{ "from": "らいてー", "to": "雷霆", "reading": "らいてい" }]
```

空の配列なら、寄せずに済んだということです。元の聞き取りは `state.speech.rawTranscript` に残っているので、寄せ方が合っているかを見比べられます。

## 回ごとの記録：`rounds`

一回分の記録が配列に並びます。`rounds[0]` が一回目（0〜30秒）、`rounds[1]` が防御（24〜40秒）、`rounds[2]` がとどめ（40〜60秒）です。記録の先頭には6桁の確認番号（`confirmCode`）も入ります。中身はどちらも同じ形です。

| 項目 | 意味 |
| --- | --- |
| `round` / `castId` | `first` か `defend`。Jevへ送るときの区別に使う番号も入る |
| `state` | Jevへ送った内容そのもの。`speech.rawTranscript` が聞き取った文字、`previous` が前の回の魔法 |
| `recipe` | 決まった魔法。`source` が `jev` ならJevの返事で、`local` ならPC内の規則で決まっている |
| `jev` | Jevの返事そのもの。届かなければ `null` |
| `guard` | 防御の回だけ入る。下の表を見る |
| `speechEntries` / `usedFallback` | 採用した聞き取りと、確定が間に合わず途中の結果を使ったか |
| `corrections` | 聞き取りの書き方を辞書へ寄せた記録 |
| `events` | その回の場面の切り替わりと確定の時刻 |
| `rawPoints` / `displayPoints` | 本人が描いた点列と、表示用に間引いた点列 |

### 防御の回：`rounds[1].guard`

| 項目 | 意味 |
| --- | --- |
| `enclosed` | 狙いの印を囲めたか。囲めなくても防げるので、失敗の印ではない |
| `rings` | 何重に囲んだか |
| `moved` | 囲めず、一番近い線を印の前へ運んだか |
| `kind` | 盾の形。`ring`（輪）、`wall`（横長）、`pillar`（縦長）、`orb`（小さい動きか、線が無いとき） |
| `layers` | 重なった層の数。1〜5 |
| `style` | 止め方。`block`（受け止める）、`reflect`（弾き返す）、`erase`（かき消す） |

人に試してもらったとき、`enclosed` が `false` ばかりなら、印の大きさか位置を見直す材料になります。

## 戦い全体の項目

`sessionId`、`scope`、`inheritedNodes`（一回目から引き継いだ光点の数）、`mode`、`calmMode`、`audio`、`composite`、`measurement`、`diagnostics` は戦い全体で一つです。
