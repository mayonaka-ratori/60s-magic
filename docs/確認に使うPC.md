## 測った値（2026年9月20日まで）

多くは、一回目の受付が14秒だったころ（全体が60秒のころ）の版で測った値です。90秒にしてからは測り直していません。

### 音声認識

ゲームは毎回「先頭から今まで」を聞き直すので、声が伸びるほど一回の時間が延びます。

| PC | モデルと動かし方 | 声の長さ | 一回の認識時間 |
| --- | --- | --- | --- |
| Mac | `kotoba-v2.0-mlx`（MacのGPU） | 2.6〜2.7秒（合成音声） | 0.86〜1.08秒 |
| Mac | 同上 | 約13秒（ゲーム中） | 約1.25秒 |
| Mac | `small`（CPUだけ、5コア） | 0.4〜13.2秒 | 1.07〜1.70秒 |
| Windows | `kotoba-v2.0`（NVIDIAのGPU） | 合成音声一回分 | 0.11〜0.13秒 |

MacのGPUでは約13秒の声で約1.25秒だったので、「順番に」の一回目（14秒）なら最後の声を待つ2秒の中に収まる見込みです。「同時に」の一回目（18秒）の長さではまだ測っていません。CPUだけでは声が短くても約1秒かかり、これは声を音の特徴に変える処理が15秒ぶんを計算するためです。CPUで動かしたときは、前のプレイの演出と取り合って出だしの認識が4.5秒かかった回がありました。

### 描画（Mac）

| 条件 | 平均fps | 気になった点 |
| --- | --- | --- |
| カメラと音声認識を同時に使用 | 44.5 | 手が画面の端に出ると見失う（その後、しきい値を直した） |

### 手の認識

今はまずMacのGPUで試し、使えないときだけCPUへ戻します。GPUで動いたときの速さはMacでまだ測っていません。確認用の記録の `diagnostics.camera` で、`delegate` がGPUかCPUか、`detectMs` の平均がいくつかを見てください。平均が10ミリ秒を超えていたら重い状態です。`?hands=cpu` で、わざとCPUで動かして比べられます。

## 速さを自分で測る

準備できているモデルを同じ音声で比べられます。

```
npm run make:speech-fixtures   # 確認用の日本語音声をPC内で作る（Macは say、WindowsはSystem.Speech）
npm run benchmark:speech       # 準備できているモデルを全部測る
npm run benchmark:speech kotoba-v2.0-mlx small   # モデルを選んで測る
```

結果は `.local-speech/speed-report.json` に残ります。ゲームでは、受付の終わりまでの声の認識が、最後の声を待つ2秒以内に終われば、最後の言葉が魔法に間に合います。

測る長さと待つ時間は、ゲームの時刻の表（`src/game/rounds.ts`）から読みます。声は二つの遊び方の受付の最長までを4つの長さに分けて測り、間に合うかどうかは最後の声を待つ時間と比べて判定します（2026年9月23日に直した。直した後の道具で、Macではまだ測っていません）。

## 気をつけること

- `mlx`（MacのGPUで動かす仕組み）は Apple Silicon の Mac でしか動きません。Windows と Linux では自動で `faster-whisper` になります。
- 音声認識も手の認識も画面の描画もGPUを使うので、GPUの取り合いが起きないかを次の確認で見てください。
- Linux の作業環境（Claude Code など）では画面の描画がソフトウェア処理になり、1秒に1コマほどしか描けないので、ブラウザーの通し試験は時間切れになります。単体の試験と型の確認は通ります。ブラウザーと音声の試験はMacで走らせます。
- 実際の人の声での精度と遅れは、まだ確かめていません。
